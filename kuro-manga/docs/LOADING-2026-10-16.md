# Catalogue loading repair — 16 October 2026

Base commit: `43eb63dfb04d351da889951a58b3917f41094af7`.

This change improves the existing approved MangaDex loading pipeline. It does
not add Comix or claim that all directory entries are working reader providers.

## Verified causes

Cold catalogue cards previously needed separate inventory, chapter-list and
page-preparation requests, plus rating checks when no current approval existed.
Every title still requires one fully decoded chapter. Repeated warm operation
and metadata reads also crossed the Redis HTTP boundary even while fresh.
Reader preparation could poll up to 260 times, and periodic route checks could
overlap an ongoing check.

The current live directory contains 1,236 entries: 2 content-eligible, 1,213
restricted and 21 blocked. Of these entries, 116 declare an adapter; declaring
an adapter does not establish current access, supported ratings or complete
reading support. Comix declares no adapter or verified active website. Existing
source-specific integration and positive content evidence remain necessary.

## Implementation

- `GET /api/catalogue/readable/qualify` combines canonical rating approval,
  shared proof lookup, smallest candidate chapter selection and one bounded
  full-page validation step. It accepts provider/title identity only. Pending
  responses contain progress counts and no reading tickets.
- Qualification state and completed proofs are shared across hosted instances.
  Existing complete proofs skip chapter/image work. Long checks resume completed
  pages, and corruption/revocation still requires fresh verification.
- The server advertises `qualificationVersion: 1` for MangaDex. The client uses
  the combined path when advertised and retains its existing path for earlier
  directories. Fresh approved titles still require a complete chapter proof.
- A bounded per-function cache holds up to 240 results / 4 MiB, retains each
  shared row's original expiry and returns copies. It never caches the readable
  inventory or revocation markers. Rating evidence retains its 30-second limit.
- Identical in-flight image reads share work within the same cancellation
  context and revocation generation. Existing image limits remain unchanged.
- Reader polling is bounded by 40 attempts and a 60-second time budget. Slow
  checks stop with a retry action that resumes saved progress. Periodic route
  checks no longer overlap an existing check. Temporary chapter failures stop
  qualification from repeatedly trying further chapters during the same outage.

No new application dependency, credential, database migration, provider bypass,
content-policy exception, or native installer change is included.

## Verification

- Node **22.23.3**, dedicated Redis **6.2.14**: **295 passed, 0 failed, 0 skipped**.
- Browser suites: qualification **6**, strict content **16**, prior performance
  **4**, provider loading **10** — **36 passed**.
- Build validates original Metro export integrity, referenced web resources and
  existing APK/EXE hashes. The immutable application export is preserved.
- New checks cover cold one-request qualification, complete page decoding,
  corruption, resumable progress, concurrent calls, shared Redis proof reuse,
  cross-instance revocation, malformed proofs, source cooldowns and reader retry.

Controlled browser fixtures displayed a cold Home cover in **1,370 ms** and a
cold Search cover in **1,143 ms**, using one combined qualification request.
Warm fixtures displayed covers in **1,301–1,369 ms**, without per-title readiness
or chapter requests. These are isolated fixture timings, not live guarantees.
A cache regression performs 50 fresh repeat reads with **zero additional
coordination reads**, then confirms that expiry forces a fresh load.

The earlier performance browser fixture now accepts both readiness endpoints;
its requirement that expired or another title's proof cannot display a cover
remains intact.

## Remaining provider work

All-provider reading remains incomplete. Missing connectors, metadata-only and
external platforms, unsupported rating contracts, changed websites, and access
restrictions require different source-specific work. Comix additionally needs a
compatible catalogue/chapter/page integration; its current upstream extension
uses a browser-based data path. A directory switch cannot supply that engine.
This repair does not bypass challenges or weaken the user's strict content and
complete-chapter requirements. Live render speed still depends on upstream
image latency and the size of a cold qualifying chapter.
